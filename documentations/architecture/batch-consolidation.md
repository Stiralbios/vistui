# Vistui Batch Consolidation System

## Context

Raw messages alone are not ideal long-term memory. The batch consolidation system processes older messages during idle periods and distills them into three structured memory objects:

- **Events** — summaries of contiguous message sequences within a Chat.
- **Topics** — titled, additive running summaries of recurring themes across non-contiguous messages in a ChatGroup: the body only grows (earlier lines stay, new ones are appended); the title can be reworded.
- **Facts** — small snippets of the current state of one thing about the user or world in a ChatGroup (no history: a changed truth fully replaces the fact; two conflicting facts never coexist).

The system is intentionally lazy: it does not need to run after every message. Modern chat context windows handle recent history; Vistui handles long-term memory.

Two pipelines enrich every message, independently of consolidation:

- **Embedding pipeline** — computes the `embedding` vector.
- **Salience pipeline** — computes the `salience_score`.

These run for all messages, including the most recent protected messages, and are not
prerequisites for consolidation: a message is consolidated as soon as it leaves the
protected window, whether or not it is already embedded and scored. Events, Topics, and Facts that are rewritten by a consolidation pipeline have their `embedding` and `salience_score` cleared and later regenerated by the same embedding/salience batch jobs.

## Goals

1. Ensure every message has an embedding and a salience score.
2. Consolidate older messages into richer, more compact memory.
3. Run only during inactivity to avoid interfering with interactive chat.
4. Support pause/resume and graceful shutdown at almost any point.
5. Resume automatically after a server restart without losing work.

## Non-goals

- Real-time memory updates.
- Re-processing edited messages after they have been consolidated.
- Cross-ChatGroup consolidation.

## Timing and triggers

- The worker starts after `batch_inactivity_seconds` of no message activity (default 1 hour).
- Any new message pauses the worker gracefully: the current LLM sub-task is allowed to finish, but no new sub-task is started.
- A manual trigger endpoint is available for testing (`POST /admin/batch/trigger`).

## Worker design

- **Single worker.** Only one consolidation process runs at a time to avoid LLM rate limits and keep the design simple.
- **In-process scheduler.** APScheduler is embedded in the FastAPI application, using a Postgres `SQLAlchemyJobStore`.
- **Graceful stop.** The worker checks a `should_stop` flag between sub-tasks. If set, it stops before the next step.
- **Resume on restart.** Processing state is persisted in the database. On startup, the scheduler loads pending work and continues.

## Processing state machine

The embedding and salience stages are queued by the message columns themselves —
exactly like memory objects. A NULL column is a waiting marker:

- `embedding IS NULL` → waiting for the embedding stage;
- `salience_score IS NULL` → waiting for the salience stage.

A failed round rolls back, the column stays NULL, and the next round retries for free.
The `processing_state` JSONB only carries the LLM consolidation flags plus retry metadata:

```json
{
  "event": "waiting | processing | done | failed",
  "topic": "waiting | processing | done | failed",
  "fact": "waiting | processing | done | failed",
  "retry_count": 0,
  "last_failure_at": null
}
```

Rules:

- `embedding` and `salience` run for all messages, regardless of protected window.
- A chatgroup with `use_salience` false opts out of salience scoring: its
  messages keep `salience_score = NULL` permanently (nothing is fabricated) and the
  selection query excludes them.
- `event`, `topic`, and `fact` only run for messages outside the protected window (`protected_message_count` most recent messages in a Chat — the protected messages are never added to facts, events or topics). The window size is configured per chatgroup via its config; deployments change the default with the `VISTUI_PROTECTED_MESSAGE_COUNT` setting (10).
- The most recent messages are excluded from consolidation to avoid complications from edits, rerolls, and deletions.
- Older messages are processed first.
- Each pipeline can fail independently; a failed message keeps its waiting flag and
  is retried by later rounds.
- A processing step that exceeds `processing_timeout_seconds` is marked `failed`.
- Any message PATCH carrying `full_text` bumps `edited_at` — the column records when
  the text was last written and is set at creation too. When the new text actually
  differs from the stored one, everything derived from it is requeued (embedding,
  salience, consolidation flags); identical text or role-only edits touch nothing
  derived. `/admin/reembed` (after an embedding-model switch) nulls every vector, which
  requeues everything downstream.

## Consolidation pipelines

### Embedding pipeline

**Scope:** batch (up to `VISTUI_BATCH_EMBEDDING_LIMIT` messages per round, 32 by default).

1. Select the oldest messages with `embedding IS NULL`.
2. Send each `full_text` to the configured embedding provider.
3. Store the embedding vector (a failed round rolls back and the next round retries
   for free).

If an Event, Topic, or Fact has `embedding = null`, it is also eligible for this pipeline.

### Salience pipeline

**Scope:** batch (up to `VISTUI_BATCH_SALIENCE_LIMIT` messages per round, 5 by default).

Salience is scored by the **decision model** (an ollama System One model such as
`d3:4b`, see [llm-provider.md](llm-provider.md)), not by a chat completion:

1. Select the oldest messages with `salience_score IS NULL`
   (up to `VISTUI_BATCH_SALIENCE_LIMIT` per round, 5 by default, oldest first) — the
   stage does not wait for the embedding stage. Chatgroups
   with `use_salience` false are excluded by the query itself: their NULL score is
   permanent and would otherwise clog the queue forever.
2. For each message, one `decide()` call (element per element, like the other batch
   stages): the state carries the chatgroup description plus the single message
   (role, text), and one `score` question named `salience` is asked against the
   chatgroup's `salience_rubric` (2-10 ordered levels, lowest first; 5-level default:
   trivial → critical) with the chatgroup's `salience` instruction template.
3. Normalize the probability-weighted rubric index to `[0, 1]` (divide by the number
   of rubric levels minus one) and store it as `salience_score`.

ChatGroups with `use_salience` false opt out: their messages keep
`salience_score = NULL` (nothing is fabricated), and the search formula passes the
neutral salience (1.0) for them. A failed round rolls back — the column stays NULL and
the next round retries for free.

Events, Topics, and Facts with `salience_score = null` are scored the same way by the
**memory salience stage**: one `decide()` call per object, with the object's
`full_text` as the state entry (up to `VISTUI_BATCH_MEMORY_SALIENCE_LIMIT` objects per
round per model, 32 by default). Objects of opted-out chatgroups keep their NULL score.

### Event pipeline

**Scope:** per Chat.

Events are built incrementally, one message at a time — the model decides the
boundaries, there is no fixed block size:

1. Select the oldest messages with `event = waiting` outside the protected window
   (up to `VISTUI_BATCH_EVENT_MESSAGE_LIMIT` per round, 10 by default).
2. For each message, load the Chat's last event (greatest `end_at`).
3. A Chat without events opens a new event directly — no LLM call is spent on the
   boundary question.
4. Otherwise one `decide()` call against the decision model (task `event_boundary`):
   the state carries the chatgroup description, the last event (summary, time range),
   and the message (role, text, created_at); one `choice` question named `boundary` is
   asked with the chatgroup's `event_boundary` instructions and
   `event_boundary_criteria` (extend / new / mixed by default). The highest-probability
   criterion wins.
5. Apply the decision:
   - **new** — create a new event from the message alone.
   - **extend** — the message joins the last event: its summary is rebuilt from the
     full member list through the `event_summary` prompt, the time range grows,
     `edited_at` is bumped, and the embedding/salience columns are cleared for
     regeneration.
   - **mixed** — the message spans the boundary: it concludes the last event (rewritten
     including it, like extend) and opens the next one; the message is linked to both.
6. Link the message to every event it belongs to, mark it `event = done`.

Summaries are always rebuilt from the event's full member message list — never from
the previous summary — so they cannot drift from the sources. Event spans are
unbounded: an event grows as long as the boundary decisions say "extend", and a
round may create many events or none at all.

### Topic pipeline

**Scope:** per ChatGroup.

The topic pipeline uses one LLM call per message.

A topic is a short title followed by the additive running summary of one recurring theme:
updates return the complete new text — the body only grows (earlier lines kept, new ones
appended; the title can be reworded) — so the theme's evolution stays visible inside it.

1. Select the oldest unprocessed message (`topic = waiting`) outside the protected window.
2. Search existing Topics in the ChatGroup by embedding similarity (the same retrieval ranking logic as interactive retrieval). If the message is not embedded yet, no existing topics are offered and the LLM can only create new ones.
3. Send the message and the top matching topics to the `topic_candidate` LLM prompt. The
   rendered prompt introduces both participants by name (chatgroup config
   `user_name`/`assistant_name`, generic fallbacks when unset) and attributes the new
   message to its speaker.
4. The LLM returns a list of actions: create a new topic, update an existing topic with its
   complete new text (the body only grows: earlier lines kept, new ones appended; the title
   can be reworded), or skip a topic.

Apply each action:

- **create** — create the Topic, link the current message to it, leave `embedding` and `salience_score` as `null` for the embedding and salience pipelines.
- **update** — rewrite the topic text in place, link the current message to it, clear the topic's `embedding` and `salience_score` to `null`.
- **skip** — do nothing.

Mark the message as `topic = done`.

### Fact pipeline

**Scope:** per ChatGroup.

The fact pipeline uses one LLM call per message. A fact is a short title followed by a small
body describing the current state of one thing. The body holds no history — when the truth
changes it is fully replaced (the title can be reworded), and two conflicting facts never
coexist (earlier states remain visible in events and topics). Protected messages are never
added to facts until they age out of the window. A fact itself is never protected from
updates: once the updating message is outside the window, the fact can be rewritten in place.

1. Select the oldest unprocessed message (`fact = waiting`) outside the protected window.
2. Search existing Facts in the ChatGroup by embedding similarity.
3. Send the message and the top matching facts to the `fact_candidate` LLM prompt. The
   rendered prompt introduces both participants by name and attributes the new message to
   its speaker, like the topic candidate prompt.
4. The LLM returns a list of actions: create a new fact, update an existing fact with its
   replacement text (the new current state), or skip a fact.

Apply each action:

- **create** — create the Fact, link the current message to it, leave `embedding` and `salience_score` as `null` for the embedding and salience pipelines.
- **update** — rewrite the fact text in place, link the current message to it, clear the fact's `embedding` and `salience_score` to `null`.
- **skip** — do nothing.

Mark the message as `fact = done`.

A fact is rewritten in place when the underlying truth changes (e.g., "Mom is sick" → "Mom is on vacation").

## Work scheduling

The worker operates in rounds:

1. Run the batch stages once, each in its own transaction: `embed_messages` (up to
   `VISTUI_BATCH_EMBEDDING_LIMIT` messages), `embed_memory_objects` (up to
   `VISTUI_BATCH_MEMORY_EMBEDDING_LIMIT` objects), the salience round (up to
   `VISTUI_BATCH_SALIENCE_LIMIT` messages), and the memory salience stage (up to
   `VISTUI_BATCH_MEMORY_SALIENCE_LIMIT` objects).
2. Then run the consolidation pipelines in order: `event` (up to
   `VISTUI_BATCH_EVENT_MESSAGE_LIMIT` messages), `topic`
   (`VISTUI_BATCH_TOPIC_MESSAGE_LIMIT`), `fact` (`VISTUI_BATCH_FACT_MESSAGE_LIMIT`).
   Every stage processes its oldest waiting messages one by one, each message in its
   own transaction. All these limits are configurable through the `VISTUI_BATCH_*`
   environment variables (`backend/settings.py`).
3. Commit results and state changes after each sub-task.
4. Check `should_stop`. If true, exit the round.
5. Repeat.

This design ensures that:

- Work is fine-grained and resumable.
- A server restart loses at most the in-flight LLM call.
- A graceful stop can occur between any two sub-tasks.
- A message enters event/topic/fact processing as soon as it is outside the protected
  window, regardless of where the embedding and salience stages are.
- The worker is message-oriented, not ChatGroup-oriented.

## Idempotency and retries

- A sub-task is considered complete only after the database commit. Each message is
  its own sub-task, so a failure never rolls back the messages already handled in
  the same round.
- If a message's LLM or decision call fails or returns a malformed answer, the message
  keeps its `waiting` flag — later rounds retry it for free — with the failure recorded
  on it (`retry_count`, `last_failure_at`) and counted in the admin status
  (`recent_failures`).
- A stage-level crash with no single message to attribute marks the round's anchor
  message `failed` as a safety net; its embedding/salience counterparts stay NULL and
  retry for free.

## Interaction with message edits

- If a message is edited after it has already been processed, its processing flags are **not** reset.
- This is an accepted limitation due to the difficulty of re-deriving downstream memory.
- The `protected_message_count` window reduces the chance of editing affecting unprocessed work.

## Failure handling

| Scenario | Behavior |
|----------|----------|
| LLM call fails or returns malformed JSON | The message keeps its `waiting` flag with the failure recorded (`retry_count`, `last_failure_at`); the round continues with the next message, later rounds retry it. |
| Decision call fails or returns a malformed answer | Same: message stays `waiting`, retried next round. |
| Event rewrite invalidation | Like topic/fact updates: `edited_at` bumped, `embedding` and `salience_score` cleared, the memory stages regenerate them. |
| Embedding fails after LLM succeeds | Save the consolidated object without embedding, mark `failed`, retry embedding later. |
| Server restarts mid-task | In-flight call is lost; the message keeps its `waiting` flag and is retried on the next round. |
| New message arrives | Worker finishes current sub-task, then pauses. |

```json
}
```

## Performance and cost considerations

- Serial processing avoids rate limits but limits throughput.
- LLM calls dominate cost and latency.
- Embeddings and salience scores for consolidated objects are computed lazily by the embedding and salience pipelines.
- The protected window reduces churn and wasted LLM calls from edits.

## Open questions

- Should the event pipeline be scoped to Chat or to ChatGroup?
- Should failed pipelines send alerts or only appear in logs?
- Should there be a reaper job to clean up dangling links from deleted messages?
